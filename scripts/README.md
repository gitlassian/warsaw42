# Выкладка и откат

Два скрипта, чтобы выкладывать изменения в `main` без страха: перед слиянием всё проверяется, а любая выкладка откатывается одной командой.

Нужны `git` и залогиненный GitHub CLI (`gh auth login -h github.com`). Запускать из корня репозитория.

## Выложить

```sh
git switch -c my-change origin/main     # каждое изменение — в своей ветке
# ...правки, git add, git commit...
scripts/ship.sh --dry-run               # всё проверить, ничего не пушить
scripts/ship.sh                         # выложить
```

Что делает `ship.sh`:

1. Проверяет, что ты не в `main` и все изменения закоммичены.
2. Вливает в ветку свежий `main`. Если есть конфликт, останавливается и перечисляет файлы. Наружу ничего не уходит.
3. Показывает, какие файлы меняются. `docs/` и `postman/` считаются безопасными. Для всего остального (код приложения, `.github/`) просит ввести `yes`. Отдельно предупреждает про миграции и `seed.sql`.
4. Запускает проверки: тесты `backend` всегда, остальные — по затронутым областям: разбор JSON в `postman/`, `npm test` / `build` / `lint` для `frontend/web`, `flutter analyze` / `test` для `frontend/mobile`. Если что-то упало, ничего не пушится.
5. Пушит ветку, создаёт PR (или берёт уже открытый) и ждёт, пока GitHub подтвердит, что его можно слить.
6. Сливает PR одним merge-коммитом.
7. Ставит тег `before-ship-<ветка>-<время>` на тот `main`, в который слил, — закладка «как было до выкладки». Печатает команду отката.

`--dry-run` проходит шаги 1–4 и возвращает ветку в исходное состояние. `--yes` отвечает «да» на вопрос про рискованные файлы. `--title "…"` задаёт заголовок PR.

Если, пока шли проверки, в `main` появились чужие изменения в коде, скрипт остановится с открытым PR. Просто запусти его ещё раз. Коммиты автообновления данных (`backend/data/`) ему не мешают.

Если проверки упали, наружу ничего не уходит. Но в ветке может остаться локальный merge-коммит со свежим `main`, и это нормально.

## Откатить

```sh
scripts/rollback.sh                     # список последних выкладок
scripts/rollback.sh 12 --dry-run        # что изменится при откате PR #12
scripts/rollback.sh 12                  # откатить PR #12 (можно и sha merge-коммита)
```

По sha откатываются только выкладки, сделанные через `ship.sh`. Для PR, слитых иначе (например, PR #1), указывай номер PR. Обычные merge-коммиты вида «Merge remote-tracking branch» скрипт откатывать отказывается: у них родители в обратном порядке, и откат стёр бы чужую работу.

`rollback.sh` создаёт в `main` новый коммит, который отменяет выкладку. История не переписывается, коммиты коллег остаются. Работает во временной копии, твоя рабочая папка не меняется. Если после выкладки кто-то правил те же строки, автоматический откат невозможен: скрипт скажет об этом и ничего не тронет.

## Важно

- **База данных не откатывается.** Если выкладка меняла миграции или `seed.sql`, а их уже применили к Supabase, `git revert` вернёт только файлы. Изменения в базе нужно откатывать отдельно.
- **Повторная выкладка после отката.** Git помнит, что ветка уже слита, и при повторном слиянии изменения молча пропали бы. `ship.sh` это замечает и останавливается. Исправляй в новой ветке от свежего `main`, либо сначала откати сам откат: `git revert <sha коммита отката>`.
- **Файлы в `.github/workflows/`** можно пушить, только если у токена gh есть право `workflow`.
- **Без force-push.** Скрипты никогда не переписывают `main`: коллеги пушат туда параллельно.
